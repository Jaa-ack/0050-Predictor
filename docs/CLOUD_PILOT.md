## 主機、權限與私人資料

2026-11-16 首個盤中窗口出現訂閱未就緒、採集心跳停滯及復原次數耗盡。唯讀堆疊採樣顯示 CPU 花在純 Python WebSocket UTF-8 驗證與行情寫入；同機提醒容器也出現健康檢查逾時。先前檢查發現 SDK 連線存在忙等，但實際採樣沒有支持它是本次主要卡點，因此沒有改寫 SDK 連線或凍結預測程式。

本次在研究帳號擁有的 `runtime/python-dependencies/` 安裝固定版 `wsaccel==0.6.7`，以單一 `twquant_wsaccel.pth` 載入，不遞迴調整既有虛擬環境權限。262 個隔離合成位元組案例與原驗證器逐一一致，包括有效文字、無效序列與不完整前綴；沒有跳過 UTF-8 驗證。重新啟動採集後確認恢復 105／105 訂閱及持續寫入。[WebSocket官方效能說明](https://websocket-client.readthedocs.io/en/latest/faq.html)亦列出此原生驗碼支援。新的 Linux CPython 雲端部署使用 `[cloud]` 額外依賴，支援有官方 wheel 的 Python 3.11～3.13；一般安裝不強制加入原生擴充。

共用小主機的採集與報告工作另設`Nice=10`，獨立發報維持原優先序。實測另確認研究群組撞到512 MiB上限，反覆回收記憶體並等待磁碟；原本09:58條件只擋新報告，無法停止較早啟動的報告。因此新增宣告日期09:58的固定單元，只停止研究報告，並將研究群組上限有界調為640 MiB，沒有擴充VM或修改其他服務。

`scripts/cloud_pilot_sqlite.py`只在研究venv載入，將連線快取設為8 MiB、關閉提交當下的自動WAL檢查點，避免小型標準磁碟的隨機寫回擠進發報路徑。WAL與FULL同步提交維持原樣，讀取者可見已提交資料；SQLite仍可在最後連線關閉時整理檢查點，原磁碟保留量亦涵蓋WAL成長。隔離測試確認提交後強制結束程序仍能恢復資料。沒有降低同步等級或刪除WAL檔。

原採集迴圈最多連續處理2萬筆，在忙碌時很久才回到心跳與覆蓋更新，造成自發停滯及監控誤判。新增的`scripts/cloud_pilot_collector.py`每輪最多512筆或0.25秒後讓出控制，沿用凍結的行情驗證、資料儲存、缺口、原供應商登入及重連規則；原訓練、預測、封印與評分來源不變。這是另外記錄摘要與版本的營運採集實作，不把它冒稱為原採集器完全未變。真實的單次I/O停頓、斷線與溢位仍保守記錄。

下午v2另加入SIGTERM與自然結束的有界收尾：停止接收後處理既有佇列，最多90秒迴圈預算，原收件時間不改寫；私人逐次回執保存處理、無效、溢位與剩餘筆數。上層自然結束先等待120秒，systemd停止寬限150秒；超時、低空間及強制中斷不能當成完整保存。報告保護窗口目前為09:28～10:17:30；上段09:58記錄是早上第一輪修復，未更改其歷史結果。

11/16當日完整53個查詢（含50檔成分股）於10:03:50.655896+08:00發布，超過準時誤差，當日依原規則不給正確信用。停頓、缺資料及復原次數保留，不回填、不刪除或替換失敗日期。重新部署時另外補記保守缺口，沒有改寫原事件或發布封印。

採集窗口結束後，在獨立私人資料庫做100秒實際盤中診斷，確認105／105訂閱、規律心跳、佇列清空及新行情持續寫入；該程序不發預測，診斷事件不加入正式試驗。這不是開盤尖峰或未來十日零缺漏保證。正式價格、逐筆資料、原始日誌與診斷工具沒有放入Git。

既有主機為美國地區 e2-micro、Debian 12、Python 3.11.2，約 1 GB 記憶體。使用專用 `/opt/twquant-pilot` 與服務帳號，程式／venv 可讀取，私人 `runtime/`、`log/`、`.secrets/` 為 0700；`.env`、憑證與私人通知設定為 0600。只搬移必要富邦身分、API Key、憑證及憑證密碼，沒有搬移整份 Mac 設定或其他供應商秘密。

憑證僅在 `.secrets/fubon/`；SDK 建構前準備私人原生日誌目錄，原始日誌不進 Git、網站、封裝或通知。服務的固定診斷碼及營運狀態可以用於通知，憑證值、帳戶物件及供應商原始資料不可傳送。

同磁碟備份使用 SQLite backup API、完整性檢查及原子替換，保留最新一份，避免十份累積快照耗盡空間。建立新備份後仍須保留至少 4 GiB；空間不足時保留原資料庫與舊備份並告警，不刪資料、不購買容量。這不是異地備援，無法防止整顆持久化磁碟毀損。

## 故障偵測、通知與復原

`scripts/cloud_pilot_watchdog.py` 位於凍結預測來源之外，只檢查運作狀態與操作固定研究服務。監控本身由 systemd 定期執行，失敗時重試。檢查包括私人設定存在、來源摘要、NTP、磁碟、資料庫、採集心跳、訂閱就緒、新行情、完整預測與發布封印、日報及備份。

採集心跳超過 30 秒、持續訂閱未就緒、或超過 120 秒未寫入行情時提出異常；收集開始時保留連線暖機時間。巡檢週期是 30 秒，不代表全部錯誤都在 30 秒內確診。盤前失敗可在 09:30 前有限重試；發報復原只在凍結程式允許的原期限內啟動，超過期限只告警，不倒填時間。

另對積壓達1024筆，或有積壓且落盤延遲超過5秒告警；加入當日觀測缺口、512MiB以上WAL、結束150秒後的收尾回執缺失／未清空。這些狀態不直接重啟正常運行的採集器，以免丟掉待存訊息。資料庫恢復或忙碌時保留既有異常，直到設定、凍結來源、資料庫與NTP皆確認可信，才可發送恢復通知。

watchdog 只可啟動／重啟本試驗的固定 service。採集的啟動與重啟共用每日預算；每個工作每日最多三次 watchdog 復原，間隔至少 120 秒，計數跨程序重啟保留。原有 service 自身的 systemd 失敗重試仍適用。供應商 fatal 記錄、來源摘要不一致、資料庫無法讀取或磁碟不足不會被清除；不自動更換秘密、刪資料、重建資料庫、調模型或操作交易。

通知使用同主機既有私人 Telegram 機器人的發送 API，收件者已確認是設定中的私人使用者；不使用長輪詢，不與原提醒機器人競爭更新。只送固定異常碼、有限復原狀態、恢復及期末完成訊息，成功通知去重；傳送失敗會重試，異常先恢復仍會補送恢復紀錄。

整台 VM 停機或對外網路中斷期間，同機監控不能立即通知；通道恢復後才可傳送。這是有界的固定監督程式，不是 ChatGPT 持續在線，也不代表任意程式錯誤都能自動修補。超過重試預算或需要修改程式時須人工處理。沒有配置另外付費的站外監控或公開供應商資料。
